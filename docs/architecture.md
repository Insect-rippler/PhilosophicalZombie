# 两条线：模型调用 与 tick

整个系统只有两条线，其它都是它们的细节。分清这两条线，改动才不会互相踩。

---

## 一、模型调用线

由触发器发起：`POST /turn`（真人说话）或 `idle_tick()`（计时到、静默到期、事件吵醒）。

```
① 组装上下文（全在内存里完成，不写任何中间文件）
   a. search_text：session 尾部 + 本轮 user 消息，约 500 字
   b. 三路检索：memory（向量）· lorebook（正则）· skill（正则）
   c. 拼接：system → appearance(图) → session → 三块 → state → plan → user

② 发请求
   stream=true，工具表随行

③ 解析
   delta / tool 事件实时推给前端
   工具调用逐条取出

④ 执行工具
   启动：建计时器、写 state、给回执
   拒绝：回执写原因，不渲染动作（台词照发）
```

### 为什么检索必须放在组装里

检索的查询词是 `search_text`，而它**必须包含本轮 user 那句话**。

```
如果先发请求、拿到工具结果后再检索：
    用户这一句要到下一轮才参与检索，本轮召回的是旧话题
```

所以顺序只能是：先拼查询词 → 检索 → 再拼完整上下文 → 发请求。

### 检索在内存里，不落盘

```
memory      向量检索（model/bge-small-zh-v1.5，512 维）
lorebook    正则/关键词匹配
skill       正则/关键词匹配
```

三者都只返回字符串块，直接拼进消息，不经过任何 JSON 文件。
落盘的只有检索不到的原始料（slices / blocks / lorebook / skill），那是数据，不是中间产物。

### 一次调用的滞后（已知且可接受）

工具在**本轮请求之后**才执行，所以：

```
本轮工具产生的结果（她刚看见了什么、刚走到哪）
        ↓
不参与本轮的检索
        ↓
下一轮才进 search_text
```

对用户对话回合，这意味着“她刚发生的事”要下一句才影响召回；
对自主回合没有影响——自主回合本来就没有 user 消息，search_text 用的是 session 尾部，
下一轮再用也一样。

这是设计选择，不是缺陷：**检索的输入是“已经说过的话”，不是“正在发生的动作”。**

### search_text 抓什么

`core.search_text_make()`：

```
抓     user / assistant 的正文，以及 active 的 description 与 scene
顺序   新的在前
截断   超过 harness.retrieval.queryTurns.maxChars（默认 500）就停
```

不按时间窗口截断——睡一觉醒来，睡前的几轮仍要参与检索。

## 二、tick 线

`TICK_SECONDS = 60`，每 60 秒一次，由 `idle_loop()` 驱动。

```
① 结算计时器   timers.settle()      到期的动作落账：位置、状态、数值
② 结算生理     timers.advance()     按真实流逝推进 metabolism
③ 更新角色文件 写回 character.json
④ 判定事件     events.roll()        整点才掷（重构后）
⑤ 更新 state   下一次组装时现算，不落盘
```

### 顺序问题（要统一）

用户给的顺序是 **计时器 → 生理**，代码现在是 **生理 → 计时器**：

```python
# 现在 server.idle_loop()
timers.advance()      # 先结算生理
timers.settle()       # 再结算计时器
```

差别在于：动作完成时的奖励（吃了东西、睡醒）**应该在接受这段时间的流逝之前还是之后**生效。

建议统一成用户给的顺序：

```
先 settle：把这一分钟内到期的事落账（她吃完了、走到了）
再 advance：按流逝推进生理
```

理由：落账产生的是“事件时刻”的值，推进是“之后一段时间”的累积；先落账再推进，
时间线才对得上。改动很小（交换两行），但要同步改 `lastUpdate` 的语义——需要一次验证。

### tick 不调用模型

```
tick 只结算、判定、写文件
唯一例外：事件命中的子代理（重构后，每小时最多一次）
```

### tick 不推送

前端每 6 秒轮询 `/history` 与 `/state`。tick 里什么都没发生时不产生任何网络流量。

---

## 三、两条线的边界

| 谁拥有 | 模型线 | tick 线 |
|---|---|---|
| 计时器 | 创建（执行工具时） | 结算（到期时） |
| 生理 | 不写 | 唯一写入者 |
| 事件 | 接收（写进 state） | 产生（判定 + 子代理） |
| state | 读 | 算（下一轮组装时现算） |
| session | 写（助手消息、工具回执） | 不写 |
| 检索 | 只读（在内存里组块） | 不参与 |
| plan | 读（写只经 plan 工具） | 读（事件不改进度） |

**一句话：模型线负责“她做了什么”，tick 线负责“世界过了多久”。**

---

## 四、改动的落点

```
事件重构      改 tick 的第 ④ 步 + 删地图依赖
state 扩容    改模型线第 ① 步的 state 段 + tick 第 ⑤ 步
body 交还     删模型线里的一次子请求（②③ 之间）
```

三件事都落在同一条线上，所以按 事件 → state → body 的顺序做，只动一轮。
